# 允许的问题类型清单

所有阶段（5A/5B/5C/5D/5E/8）的 `issues[].type` **只能**取自下表。出现表外类型，Agent5E 必须判为格式问题并要求修正。

| type | 含义 | 判定要点 |
|------|------|----------|
| 与上位法或规范不一致 | 预案表述与上位法、强制性标准冲突 | 必须给出上位法条文原文对比 |
| 低于法定要求 | 预案要求宽松于法定最低要求 | 须指出法定量化/程序要求 |
| 缺失法定必备内容 | 缺少法规或编制导则要求的章节/要素 | 须指出要求该要素的条文 |
| 职责/权限/主体不明确 | 未明确责任主体、权限边界或"由谁做" | 须指出法定应明确的主体 |
| 法定程序缺失 | 缺少法定的审批、备案、评审、公布、启动/终止等程序 | 须指出程序性条文 |
| 法定时限缺失/不合理 | 缺少或长于法定时限（如报告时限、修订周期、演练频次） | 须给出法定时限 |
| 法定衔接不清 | 与上级预案、同级相关预案、下级预案衔接缺失或矛盾 | 须指出要求衔接的条文 |
| 强制性条文表述不符合要求 | "应当/必须"被写成"可以/宜"等弱化表述 | 须对比强制性条文 |
| 必要附件/要素缺失 | 缺少法定附件（通信录、物资清单、图表、协议等） | 须指出要求附件的条文 |
| 引用法规或条款错误 | 引用的法规名称/文号/条款号错误、已废止或已被修订 | 须给出正确名称或有效性结论 |

## 严重程度

| severity | 标准 |
|----------|------|
| high | 违反法律、行政法规或强制性标准的明确要求；缺失核心法定要素；引用已废止法规 |
| medium | 违反部门规章、地方性法规、推荐性标准要求；要素不完整；表述弱化 |
| low | 引用格式瑕疵、条款号笔误、非核心要素表述不严谨 |

## 每个 issue 的必备字段

| 字段 | 要求 |
|------|------|
| `issue_id` | 全局连续编号（5A: `P-xxx`；5B: `P2-xxx`；5C 起统一重编为 `P-xxx`） |
| `clause_id` | 关联的条款编号；同一问题涉及多条款时填首个条款 |
| `affected_clauses` | 该问题涉及的**全部**条款编号数组（单条款问题填单元素数组） |
| `quoted_text` | **错误原文**：从预案正文逐字摘出的出错文字，≥10 字。批注就锚定在这段文字上，所以必须能在原文中精确匹配。不得为空、不得用整段代替、不得改写或概括 |
| `clause_count` | `affected_clauses` 的长度，必须与数组一致 |
| `finding_scope` | `systemic`（同一缺陷跨 ≥3 条款）/ `clause_level`（单条或 2 条款）。5A 聚合、5C 归并后均须标注 |
| `type` | 取自上表 |
| `description` | 具体问题描述，必须写清三件事：**预案怎么写的 / 法定怎么要求的 / 差在哪**。禁止只写触发条件（如"涉及X但未涉及Y"），那是规则命中日志，不是问题描述 |
| `reference` | **支撑本发现的知识库内依据**的法规全称，不得缩写；必须能在 `law_metadata.json` 中按 `law_name` 精确匹配。注意语义：它是「凭什么说这是问题」的权威依据，**不是**预案里被质疑的那个引用 |
| `challenged_citation` | 仅 `引用法规或条款错误` 类型必填：预案中**被质疑的那个引用**（法规名/文号/条款号）。此字段**不参与**依据门禁——被质疑的引用本地没有是常态，不构成「无依据」 |
| `article` | 具体条款号（如"第二十三条"）。**不得为空**——空条款号意味着依据未落实，该命中应降级为 `advisory` 而非问题 |
| `clause_text` | 该法规条文原文摘录，≥30 字，**必须来自知识库**，禁止凭记忆撰写 |
| `basis_source` | 依据文本所在的本地法规文件名 |
| `chunk_id` | 依据条文在知识库中的 chunk 编号（可追溯性凭证） |
| `severity` | high / medium / low |
| `suggestion` | 修订建议，只能是法律法规层面的修订方向。**不得为空**，且必须指向具体的法定表述或应补充的法定要素 |

## 字段级铁律（实跑暴露的失效点）

**0. `reference` 与 `challenged_citation` 不得混填。** `引用法规或条款错误` 类型的语义与其他类型相反：需要写下来的既有「预案引错的那个东西」，也有「凭什么说它错了」。前者填 `challenged_citation`、不参与门禁；后者填 `reference`、参与门禁。实跑中有 3 条问题把预案引用的其他预案名（《国家危险化学品事故应急预案》等）填进了 `reference`，门禁按「不在知识库」剔除——结论对但理由错；而一个**真的**引用错误（如预案引《安全生产法》第九十九条而该法无此条）形状完全相同，会被同样误剔。

**1. `reference` 必须在知识库内。** 实跑 52 个问题里 34 个引用了 `laws/` 中不存在的法规——这些"问题"在本系统的证据体系内不成立。`reference` 取不到 → 记 `advisory` + `kb_gap_report.json`，不生成问题。

**1b. 依据按数组判定，不按单个字段判定。** 一个问题可以有多条 `legal_basis`。只要**任一条**在知识库内，该问题即成立，库外条目摘除并记入 `kb_gap_report.json`。实跑中有问题同时引了《突发事件应对法》第八十六条（库外）与《江西省突发事件应对条例》第四十九条（库内），只查 `reference` 单字段就把它整条剔掉了，而它有合法的库内替代依据。

**2. `article` 与 `suggestion` 不得为空。** 实跑中只有 5/52 有条款号、0/52 有修订建议。缺条款号说明只匹配到法规名而未定位到条文，依据不成立；缺修订建议则用户拿到问题也不知道该改什么。两项缺一即降级为 `advisory`。

**3. `quoted_text` 不得为空。** 实跑批注全部锚在整段上（最多一段挂 5 条批注），审阅者看不出这段里哪句话错了。交付件的价值在于"指着这句话说它违法"，所以必须逐字摘出出错文字。摘不出具体文字，说明问题描述停留在"这段大概缺点什么"的层面，尚不构成可交付的问题。

**4. 同一检查点跨条款只出一个问题。** 实跑 52 个问题去重后只有 10 个不同发现，最重复的一条出现 19 次——同一规则在 19 个条款各发一个编号。同一 `type` + 同一 `reference` + 同一 `article` + 同一缺陷成因 → 合并为一条，用 `affected_clauses` 列出全部条款。问题编号数应反映**不同缺陷的数量**，不是命中次数。

若无法确定具体条款号，须在 `reasoning` 中说明，该命中降级为 `advisory`，不得编造条款号，也不得以空条款号生成问题。
