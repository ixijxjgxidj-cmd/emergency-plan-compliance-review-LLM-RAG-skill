# Agent5A：规则快筛员

## 任务

对 `./output/clauses.json` 每一条 `CLAUSE` 执行知识库 Top20 检索 + **规则/模式匹配**，快速筛查显性法律法规合规问题。

本 Agent **不调用 LLM**，仅用关键词、模式与结构规则。定位是"广撒网"，确保显性问题不遗漏。

## 输入

- `./output/clauses.json`
- `./output/plan_profile.json`（决定启用哪些类型专属规则）
- `./output/law_metadata.json`
- `./chroma_db/`、`query_kb.py`

## 输出

- `./output/review_results_5A.json`
- `./output/kb_gap_report.json`

---

## 规则库构建的硬约束（先读这一节，违反即全阶段作废）

**规则本身不得写入任何法规名称、文号、标准号。**

规则只描述三件事：检查点、触发特征（预案文本里的关键词/模式）、应检索的法规主题。
"应检索的法规主题"是检索线索，**不是** `reference` 的取值来源。

`reference` / `article` / `clause_text` 三个字段**只能**从本次 Top20 检索结果中摘取，且 `reference` 必须能在 `law_metadata.json` 中按 `law_name` 精确匹配到一条记录。

### 依据落实门禁（每条命中都必须过）

```
规则命中
  ↓
用「触发特征 + 应检索主题」检索知识库 Top20
  ↓
能否在结果中定位到具体条文？
（① reference 命中 law_metadata.json  ② article 为具体条号  ③ clause_text 原文 ≥30 字）
  ├─ 三项齐备 ──→ 生成 issue，status=fail
  └─ 任一缺失 ──→ 记 advisory + 写入 kb_gap_report
                   不生成 issue、不占用 P- 编号、不计入 fail
```

三项缺一即降级，**不允许**用"应检索主题"里的法规名去填 `reference`，**不允许**凭记忆写条款号或条文。

### kb_gap_report.json（依据缺口报告）

规则命中但知识库无依据，是**知识库缺文件**的信号，不是预案的问题。逐条记录：

```json
{
  "generated_at": "",
  "kb_law_count": 0,
  "gaps": [
    {
      "gap_id": "GAP-001",
      "rule_id": "R-COM-06",
      "checkpoint": "信息报告时限",
      "clause_ids": ["CLAUSE-068", "CLAUSE-071"],
      "hit_feature": "命中的关键词/模式",
      "needed_law_topic": "应检索的法规主题（不写具体文号）",
      "why_blocked": "知识库中无该主题的条文，无法落实依据",
      "impact": "该检查点在本次审查中未能形成结论"
    }
  ],
  "summary": {"total_gaps": 0, "affected_clauses": 0, "blocked_checkpoints": []}
}
```

这份报告是**交付物**，Agent8 必须在报告中单列一节，明确告知用户"要完整审查本预案，还需向 `laws/` 补充哪些主题的法规"。它把"审不了"如实呈现为审不了，而不是包装成 52 个低置信度问题。

## 规则库（分层加载）

### 正误对照

错误示范（禁止这样写规则）：

```
涉及应急预案编制但未引用编制导则 GB/T 29639     ← 规则自带法规名
涉及事故报告但未明确1小时上报（依据XX条例）      ← 规则自带法定时限
涉及物资装备但未参照 GB 30077                  ← 规则自带标准号
```

正确写法：

```
检查点：涉及应急预案编制程序的条款，是否引用了知识库中现存的编制规范类法规
检查点：涉及事故信息报告的条款，是否载明了量化报告时限
检查点：涉及物资装备配备的条款，是否引用了知识库中现存的配备标准
```

> 这条硬约束的由来：实跑中规则库硬编码了《危险化学品安全管理条例》《GB/T 29639》《GB 30077》《突发环境事件应急管理办法》四部法规名，而它们都不在用户提供的 `laws/` 内。结果 52 个问题里 34 个的依据在知识库外，Agent6 只能标 `insufficient_basis_outside_kb`、Agent7 只能标 `unverified`——整条下游都在处理不成立的问题。规则自带法规名，等于绕过"知识库只能来自 laws/"这条绝对边界，是本系统最严重的失效模式。

## 同一规则的重复命中必须聚合

一条规则在多个条款上命中同一个缺陷时，**是一个问题，不是 N 个问题**。

实跑教训：`R5`（危化品许可资质）在 19 个条款上命中，生成了 19 条描述完全相同的问题；52 个问题去重后只有 17 种不同描述，`缺失法定必备内容` 37 条实际只对应 9 个不同缺陷。这让报告严重虚高，也让用户无法判断轻重。

聚合规则：

- 同一 `rule_id` + 同一 `type` + 同一 `reference`+`article` 的多次命中 → **合并为一条 issue**，`affected_clauses` 数组列出全部命中条款，`clause_count` 记数量。
- `description` 必须写成"要素级"表述，说明该缺陷在预案中的整体分布，而不是逐条重复同一句话。
- 若同一规则在不同条款命中的是**不同法条**（`reference`+`article` 不同）→ 视为不同问题，分别保留。
- 单条款独有的问题照常单独成条，`affected_clauses` 只含一个元素。

聚合后编号才分配 `P-001`、`P-002`……因此编号数量反映**不同缺陷数**，不反映命中次数。

`issue_count` 统计聚合后的问题数；每条 CLAUSE 的记录中通过 `hit_issues` 引用其涉及的问题编号，保持双向可追溯。

## 执行步骤

对每条 CLAUSE：

1. 用条款文本检索知识库 Top20（可按 `plan_type_relevance` 加权）。
2. 依次跑通用规则 + 已启用的专属规则，**逐条记录命中/未命中**。
3. 命中且能在检索结果中定位到具体法条（三项齐备）→ 记为候选命中。
4. 命中但无条文依据 → 记 `advisory` + 写入 `kb_gap_report.json`，不生成 issue。
5. 写入该条款记录。

全部条款跑完后：

6. 按上节规则对候选命中做**跨条款聚合**，生成最终 issue 列表并统一编号。
7. 汇总 `kb_gap_report.json`，把同一规则在多条款上的缺口合并为一条 gap。

## 每条 CLAUSE 记录至少包括

- `clause_id`
- `status`：pass / fail / error
- `hit_issues`：该条款涉及的聚合后问题编号数组（如 `["P-003", "P-007"]`）
- `advisory`：命中但无依据的规则列表
- `rules_checked`：全部跑过的规则号
- `rules_hit`：命中的规则号
- `skipped_rules`：因预案类型未启用的规则组 + 未启用原因
- `evidence`：Top20 前 3 条
- `retrieval_log`：query + top_hits

## 聚合后 issue 记录必须包括

- `issue_id`（`P-001` 起连续）
- `rule_id`、`type`（取自 `references/issue_types.md`）
- `description`：要素级描述，说明缺陷性质与分布
- `affected_clauses`：命中条款数组
- `clause_count`
- `quoted_text`：**错误原文**，从预案正文逐字摘出的出错文字（≥10 字），必须能在原文中精确匹配；多条款问题取首个条款中最具代表性的那句
- `reference`（**支撑本发现的库内依据**法规全称，须命中 `law_metadata.json`）
- `challenged_citation`（仅 `引用法规或条款错误` 类型填：预案中被质疑的那个引用；不参与依据门禁）
- `article`（具体条款号，禁止留空）
- `clause_text`（法规条文原文摘录 ≥30 字，须来自知识库）
- `basis_source`（依据所在的本地法规文件名）
- `severity`：high / medium / low
- `suggestion`：法律层面的修订方向（禁止留空）

### `quoted_text` 的取法

规则命中的本质分两类，取法不同：

- **"写错了"类**（表述弱化、与上位法冲突、引用错误、时限过长）→ 摘出那句错误表述本身。
- **"没写"类**（缺失法定必备内容、法定程序缺失、职责不明）→ 摘出**本应包含该内容却没有的那句**，即缺失点所在的最近上下文（如"本预案适用于……的应对工作。"用于说明适用范围条款未涵盖法定事项）。

两类都必须落到具体文字。若连缺失点所在的句子都指不出来，说明该命中只是"这段大概缺点什么"，降级为 `advisory`，不生成 issue。

## 问题编号

聚合后全局连续 `P-001`、`P-002`……不得跳号。

## 中间小结

每 20 条 CLAUSE 输出一次小结并写入 `./output/review_log.json`。

## 验收

- `review_results_5A.json` 的 CLAUSE 记录数 == `clauses.json` 条目数，无漏条。
- 每条记录都有 `rules_checked`、`rules_hit`、`skipped_rules`。
- **每个 issue 的 `reference` 都能在 `law_metadata.json` 中精确匹配**；不能匹配的 issue 一律不得存在（应已降级为 advisory）。
- 每个 issue 的 `article`、`clause_text`、`basis_source`、`suggestion` 均非空。
- 不存在两个 `rule_id`+`type`+`reference`+`article` 完全相同的 issue（聚合已生效）。
- `kb_gap_report.json` 已落盘。
- 更新 `./output/review_log.json`。
