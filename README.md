# 应急预案合规审查 Skill

对**任意类型**应急预案做逐条法律法规合规审查。RAG 知识库 + 规则快筛与 LLM 深审双轨并行 + 三步收口，输出可追溯到法条原文的问题清单、批注版预案与汇总报告。

**核心约束：法规依据只能来自本地 `laws/` 目录，取不到就如实报缺口，绝不允许凭模型记忆编造条文。**

以 Agent Skill 形式封装，可上传到支持 skill 包的智能体平台，也可在 Claude Code / Codex CLI 等环境直接驱动。

- **适用范围**：政府总体/专项/部门预案、企业事业单位综合/专项预案、现场处置方案、村（居）委会预案、重大活动保障方案；覆盖自然灾害、事故灾难（危化品、矿山、交通、火灾、环境等）、公共卫生事件、社会安全事件；国家至企业六级编制层级。
- 完整规则见 [SKILL.md](SKILL.md)，逐阶段规格见 [prompts/](prompts/)，挡位定义见 [references/strictness_levels.md](references/strictness_levels.md)。

## 架构

### 执行模型：主流程只编排，每阶段派一个子智能体

```
主流程（prompts/master.md）
  │  只做三件事：派发 → 校验该阶段验收项 → 更新 review_log.json
  │
  ├─ 派发 Agent0 ──→ 子智能体读自己那份 prompt，落盘，回报统计后结束
  ├─ 挡位选择（主流程自己做，写 review_config.json）
  ├─ 派发 Agent1 ──→ …逐个派发、逐个校验
  └─ 全部通过才输出总结
```

派发指令必须自带六项：阶段 prompt 路径、`SKILL.md` 第 2 节边界、挡位配置、输入路径、输出路径、回报格式（**只回统计，不回传产出内容**——回传全文会把主上下文重新撑爆，等于白派）。

阶段之间：核对该阶段"验收"节每一项（不能只信子智能体的回报）→ 更新日志 → 不通过最多重派一次，仍不通过就停止，**不得跳过阶段**。

唯一例外：5B 且用户提供了模型 key 时直接调外部 API，不派子智能体——既然指定了那个模型，就必须由它来审。

为什么必须这样：单一上下文串 15 个阶段会在中途质量塌陷。实跑那次 5B 在单上下文里逐条审 137 条，pass 率 96.4%，后半程等于没审。顺带换来可续跑——输出已存在且通过校验的阶段直接跳过。

### 15 个阶段

```
Agent0   预案画像与类型判定       ← 决定后续所有阶段的适用范围
   ↓
挡位选择                         ← 默认 L2；写入 review_config.json
   ↓
Agent1   本地法规盘点             ← 唯一取材口：laws/
Agent2   法规分类                 ← 效力层级 + 与本预案的相关性
Agent3   知识库构建               ← ChromaDB，按章-节-条-款切片
Agent4   预案条款拆分             ← CLAUSE-001 起连续编号
   ↓
[模型配置]                       ← 仅用户自带模型/key 时；默认跳过
   ↓
Agent5A  规则快筛 ──┐            不调用 LLM，规则 + 知识库 Top20
Agent5B  LLM 深审 ──┤            逐条调用大模型 + Top20 检索
   ↓               │
Agent5C  交叉对比审计 ←┘          决策矩阵 + 两级依据门禁 + 跨条款聚合
   ↓
Agent5C2 全文反证                「预案缺了X」放到全文范围复核，剔误报
   ↓
Agent5D  交叉审计复核             裁定"待复核"，Top20 重检索验证
Agent5E  最终审计                 编号/格式/引用/一致性/数量等式终审
   ↓
Agent6   法规依据复核             只补强依据，不新增问题
Agent7   联网核验                 只核验已发现问题，不新增
Agent8   成果汇总                 4 份交付物 + 能力边界声明
```

两处需要**二级派发**（由该阶段子智能体自己完成）：5B 模式 A 按 `batch_size` 切批；5C2 路径 2（预案 > 30000 字）按待查主张切分。

### 双轨为什么必要

| 5A 规则 | 5B 大模型 | 裁定 |
|---------|-----------|------|
| fail | fail | 保留（高置信度） |
| fail | pass | 标记待复核（疑规则误报） |
| pass | fail | 保留（LLM 独有隐性问题） |
| error | * | 保留有效那一侧 / 标记失败 |

纯规则匹配能稳定抓结构性缺陷但抓不到语义问题；纯大模型能抓隐性问题但会漏检、会编造条文。两轨独立执行、独立编号（`P-` / `P2-`）、原始结果各自落盘不被覆盖，关键在于**"两轨不一致"必须被显式处理**，而不是被合并掩盖。

### 三层规则库

规则本身**不得携带任何法规名称、文号、标准号、法定时限**——只写检查点与触发特征，依据一律现场从知识库检索取得。规则里写死法规名，等于绕过"依据只能来自 `laws/`"这条边界，这是原版最严重的失效模式。

- **第一层 `R-COM-*`**：全部预案类型强制启用（要素完整性、分级、响应启动权限、信息报告时限、预案管理程序等 18 条）
- **第二层 事件类别专属**：`R-HAZ` 危化品 / `R-MIN` 矿山 / `R-FIR` 消防 / `R-TRA` 交通 / `R-ENV` 环境 / `R-EQP` 特种设备 / `R-CON` 建筑施工 / `R-NAT` 自然灾害 / `R-PHE` 公共卫生 / `R-SOC` 社会安全 / `R-EVT` 重大活动
- **第三层 层级/主体专属**：`R-GOV` 政府 / `R-ENT` 企业 / `R-SIT` 现场处置方案 / `R-GRA` 基层组织

未启用的规则组必须写入 `skipped_rules` 并注明原因——让"没跑"和"跑了没问题"永远可区分。

## 四挡严格度

问题数的收敛来自**四个相互独立的机制**，挡位就是这四个开关的组合，不是一个模糊的松紧旋钮。

| 挡位 | 跨条款聚合 | A级依据门禁 | B级字段完备 | 全文反证 | 实跑输出 |
|------|-----------|------------|------------|----------|----------|
| **L0 原始** | off | off | off | off | **52 条**（完全复现） |
| **L1 去重** | filter | off | off | off | 17 条主张 |
| **L2 标注**（默认） | filter | annotate | annotate | annotate | 17 条，11 条带警示标记 |
| **L3 严格** | filter | filter | filter | filter | 6 条 |

`annotate` 挡照常判定但**不移出任何问题**，只把依据状态与反证结论如实标出。所以 **L3 = L2 中无任何标记的那部分**，严格包含关系——切挡位不改变任何一条问题的内容。

**L0 是独立执行链**：5A / 5C / 5D / Agent8 四个阶段改读 [prompts/L0_original/](prompts/L0_original/) 下逐字节保留的原始 prompt，并跳过 5C2。连 5A 一起换是复现 52 条的必要条件——那 34 条库外依据的问题只有原始 5A（规则自带法规名 + 无依据落实门禁）才会产生。L0 唯一刻意偏离原样的地方是**批注格式仍按四字段模板**，原始 5A 不产出的字段由 Agent8 补齐并逐条标 `derived.*`，补不到时如实退化、禁止编造。

### 怎么选

| 场景 | 挡位 |
|------|------|
| 复现原始命中、与增强链做对照（**仅危化品预案**） | L0 |
| 想知道"到底有几个不同缺陷" | L1 |
| 预案修订自查、要尽量不漏、能接受自己甄别 | **L2** |
| 出正式审查意见、交评审专家 | L3 |
| `laws/` 法规不全（少于 10 部或缺主要上位法） | L2 |

最后一条是实跑教训：那次只有 9 部可用法规，A 级门禁剔除率 24%，其中"未参照装备配备标准"一条经全文反证判定成立，却因本地缺该标准而被剔。**知识库越不全，越该用 L2 而不是 L3。**

### 挡位不改变的三件事

1. **报告必须完整披露漏斗**（各级数量与减少原因），并给出"若切 L3 剩 N 条 / 若切 L0 有 M 条"。
2. **低挡位只是不因依据在库外而移出问题**，不代表允许凭记忆编造条文。
3. **批注恒按 L3 标准取材**——带 `basis_outside_kb` / `citation_unverifiable` / `refuted_by` 标记的问题只进 `issue_list.docx` 的候选问题附录，不进批注。**分析产物全量，交付产物严格。**

## 三道防幻觉闸门

### 1. 5A 依据落实门禁

规则命中后必须**现场检索到具体法条**：`reference` 能在 `law_metadata.json` 精确匹配 + `article` 为具体条号 + `clause_text` 原文 ≥30 字。三项缺一即记 `advisory` 并写入 `kb_gap_report.json`，**不生成问题、不占编号**。

`kb_gap_report.json` 是交付物：它把"审不了"如实呈现为审不了，而不是包装成一堆低置信度问题。

### 2. 5C 两级依据门禁

**A 级（依据合法性，不过即剔除）**：按 `legal_basis` **数组**判定——遍历全部条目，任一在库即放行，库外条目摘除并登记。`引用法规或条款错误` 类型走 `challenged_citation` 分流（预案里被质疑的那个引用不参与门禁）。

**B 级（字段完备性，不过则退回补齐）**：`article` / `quoted_text` / `suggestion` 缺失时重跑 Top20 检索补齐，补不齐才剔，`reject_reason` 与 A 级明确区分。

> 混用一个动作处理两种性质的缺陷，会把可修复的问题当不成立的问题扔掉——这是上一版的实际缺陷。

**上游违约告警**：A 级剔除率 > 10% 时写入 `upstream_basis_violation_alert`。**门禁拦到东西不是门禁在正常工作，是上游失效的信号**——5A 已被要求"取不到库内依据就不生成问题"，正常流程下 A 级应拦到约 0 条。

### 3. 5C2 全文反证

**"预案缺了 X"是关于全文的命题，不是关于某个条款的命题。** 靠看一条条款断定预案缺了某要素，隐含假设是"该要素必须写在这一条"，而这个假设通常不成立。

三判定 `refuted` / `downgraded` / `upheld`，**判误报的举证责任重于判成立**：必须给出落实位置的逐字原文，且通过三要件测试（同一要素 / 有约束力表述 / 法定最小内容齐备），缺一只能降级。

用实跑数据回放的效果——**依据门禁放行的 8 条主张里，4 条（50%）仍是误报**，它们依据合法、在库、有条款号，门禁一条都拦不住：

| 主张 | 原命中 | 被什么推翻 |
|------|--------|-----------|
| 涉及事故报告但未明确法定报告时限（1小时） | 6 条 | `CLAUSE-032` 写了 15 分钟电话 / 30 分钟书面 / 1 小时法定上报 |
| 涉及应急演练但未明确法定演练频次 | 3 条 | `CLAUSE-084` 写了每年、每半年、每两年多档 |
| 涉及事故分级但未列明量化标准 | 1 条 | 量化标准就在紧随其后的 `CLAUSE-007~011` |
| 修订清单缺"演练/救援中发现重大问题" | 1 条 | 就写在下一条 `CLAUSE-091`（7.2.6） |

最后一条最值得警惕：它是 5B 深审产出的，依据精确到条号、附了逐项对照分析，**只是把清单范围看错了一条**——而清单第六项就在下一个 `clause_id` 里。这种错在任何只看单条款的审查里都发现不了。

## 交付件：批注锚定到"出错的那句话"

批注**锚定 `quoted_text` 在正文中的精确字符区间**（`w:commentRangeStart` / `w:commentRangeEnd` 包住那句话），不锚整段、不锚章节标题、不锚目录。正文四字段 + 分隔线 + 判定标签行：

```
问题：{问题类型}——{预案怎么写的 / 法定怎么要求的 / 差在哪}

错误原文：{从预案正文逐字摘出的出错文字}

依据：《{法规全称}》第X条
{该条文原文，≥30 字，逐字来自知识库}

改进建议：{依法应当如何表述或补充}

——————————
严重度：高　置信度：中　联网核验：已核验
```

判定标签强制中文值，禁止写入 `origin` / `source` / `chunk_id` / 检索日志 / 阶段代号 / 英文枚举原值，也禁止"依据来源存疑"这类自我否定表述。

落盘后**必须重开生成的 docx 自检**：`comments.xml` 定义数 == `commentReference` 数 == `commentRangeStart` 数 == 问题数，无孤儿批注；抽查 3 条批注的锚定文字是否等于其 `quoted_text`。自检不通过必须报错，不得交付。

`issue_list.docx` 的"错误原文""依据""改进建议"三列与同一 `problem_id` 的批注**逐字一致**。

> 实跑教训：上一版批注长这样——`[合规问题 P-001] 严重度:低 置信度:medium 来源:rule_only / 问题描述: 涉及危险化学品经营/储存/使用/生产但未涉及许可、资质或安全条件要求 / 法规依据: 危险化学品安全管理条例 / 依据状态(Agent6): insufficient_basis_outside_kb / 联网核验(Agent7): unverified / 核验说明: …但该法规不在用户提供的知识库中,依据来源存疑`
>
> 病根有四个：没有错误原文（挂整段，审阅者不知道哪句话错了）；依据只有法规名没有第X条没有条文原文；完全没有改进建议；判定标签混在正文里且直接吐英文枚举和阶段代号。

## 快速开始

### 1. 准备资料

```
laws/    放入法规、标准、规范性文件（PDF / DOCX / TXT / MD）
plan/    放入待审预案
```

本仓库**不含**法规文件和预案样例——法规会修订，仓库内的副本会过期变成错误依据；预案含真实联系人信息。请自行从官方来源获取现行有效版本：全国人大网、中国政府网、应急管理部及各主管部委、地方人民政府官网、国家标准全文公开系统。

一份危化品类预案的典型法规基线约需覆盖：安全生产、消防、生产安全事故应急（条例 + 预案管理办法 + 事故报告调查处理）、危险化学品安全管理、应急预案编制导则、应急装备配备标准、突发事件应对（省级条例）、预警信息发布、地方预案管理办法。

### 2. 驱动执行

```text
请读取 SKILL.md 与 prompts/master.md，严格按总控流程执行。先只执行 Agent0，完成后落盘输出文件，然后停下来汇报。
```

Codex CLI：

```bash
codex --cd emergency-plan-compliance-review --sandbox workspace-write --ask-for-approval on-request
```

默认挡位 L2，默认不需要 API key（5B 走本环境子智能体分批）。要指定挡位就直接说"用 L3"。

### 3. 逐阶段推进

**首次运行不建议全流程连跑**，在三处停下人工确认：

- **Agent0 后**：看预案类型判定对不对——判错会污染下游全部阶段
- **Agent3 后**：跑 5 条测试检索看召回质量——5A 和 5B 共用同一知识库，这是双轨设计唯一的共因失效点
- **Agent4 后**：看条款拆分覆盖度与 `element_tag` 标注

## 打包上传

```bash
python scripts/package_skill.py
```

生成 `dist/emergency-plan-compliance-review.zip`，其**根目录直接包含 SKILL.md**，可被支持 skill 包的平台直接识别。脚本会在打包后重新读取 zip 校验入口位置——"上传后提示未找到 SKILL.md"的唯一常见原因就是入口被套进了嵌套目录。

仅校验结构不打包：

```bash
python scripts/package_skill.py --check
```

默认不打包 `laws/`、`plan/`、`output/` 中的资料，需要连示例一起打包时加 `--with-samples`。

## 目录结构

```
emergency-plan-compliance-review/
├── SKILL.md            # 入口（frontmatter: name/description）
├── AGENTS.md           # Codex / 通用 agent 入口
├── CLAUDE.md           # Claude Code 入口
├── references/
│   ├── plan_type_matrix.md    # 预案类型→法规基线映射（检索线索，非可引用依据）
│   ├── issue_types.md         # 问题类型枚举 + 字段级铁律
│   └── strictness_levels.md   # 四挡严格度定义
├── prompts/
│   ├── master.md              # 总控：派发编排、执行顺序、总体验收
│   ├── 00~08/prompt.md        # 14 个增强阶段的完整规格
│   └── L0_original/           # L0 挡位用的原始 5A / 5C / 5D / Agent8（逐字节保留）
├── scripts/package_skill.py   # 打包与结构校验
├── laws/               # 用户提供的法规/标准文件（不入库）
├── plan/               # 待审预案（不入库）
└── output/             # 全部产出（不入库）
```

设计上**入口薄、规格厚**：agent 先读 SKILL.md 建立边界，再读 master.md 拿流程，每个阶段的子智能体只读自己那份 prompt。

`references/plan_type_matrix.md` 中的法规名称、文号、年份**只是"应该去找什么"的检索线索，不是可直接引用的依据**——必须在 `laws/` 有对应文件才能落实为审查依据。

## 主要产出

| 文件 | 说明 |
|------|------|
| `review_config.json` | 本次所用挡位与四个开关取值 |
| `plan_profile.json` | 预案画像与适用法规基线 |

| `kb_gap_report.json` | 依据缺口：规则命中但知识库无条文 |

| `fulltext_crosscheck.json` | 全文反证裁定 |
| `refuted_problems.json` | 被判误报移出的问题（保留完整原始记录供反查） |

## 边界

- **只审法律法规问题**。严禁纳入实操可行性、资源配置是否合理、PPE 是否合理、疏散距离是否科学、地方适配性、事故案例经验、专家经验判断、写作风格、错别字。
- **知识库只能来自 `laws/`**，不得凭模型记忆生成法规条文。取不到依据就记入 `kb_gap_report.json`，不生成问题。
- **Agent6 / Agent7 不得新增问题**：Agent6 只补强已有问题的遗漏依据；Agent7 只核验已发现问题（法规是否现行有效、条款号是否准确、条文是否一致），不得扩大范围、改变编号。
- **核验不到就记 `unverified`**，禁止编造条文或结论。
- 每一条款独立检查，每个问题可追溯到具体条款 + 具体法规条文；禁止抽样或代表性检查。

## 已知限制

- **端到端从未实跑验证。** 已验证的只有目录结构、打包脚本、zip 根入口、L0 四份原始 prompt 的字节一致性，以及用实跑数据对 5C2 判定逻辑和新旧门禁做的**离线回放**。5C2 的 `derived.*` 补齐链路、L0 下的批注生成、子智能体派发编排都是纸面设计。
- **整条流水线串行强依赖**：Agent0 判错类型污染下游全部阶段；Agent3 召回质量差会同时拖垮 5A 和 5B（两轨共用同一知识库，双轨设计唯一的共因失效点）。
- **新引入的数量等式尚未实跑校验**：`raw_issues_in − a_level_rejected − b_level_rejected_after_retry − merged_pairs == final_issues`。
- **L0 是危化品专用的**：原始 5A 的 10 条规则全部围绕危化品，审其他类型预案会大面积漏检。
- `output/model_config.json` 会包含 API key，已在 `.gitignore` 中忽略，请勿提交。
- Agent7 联网核验会向法规官网发起请求；无网络时相应问题标为 `unverified` 并据此降低置信度。
