# 应急预案合规审查 Skill（通用版）

对**任意类型**应急预案做逐条法律法规合规审查，输出可追溯的问题清单、批注版预案与汇总报告。

这是一个 **RAG + LLM 双轨审查工作流**，以 Agent Skill 形式封装，可上传到支持 skill 包的智能体平台，也可在 Claude Code / Codex CLI 等环境直接驱动。

- **适用范围**：政府总体/专项/部门应急预案、企业事业单位综合/专项预案、现场处置方案、村（居）委会预案、重大活动保障方案；覆盖自然灾害、事故灾难（含危化品、矿山、交通、火灾、环境等）、公共卫生事件、社会安全事件。
- **法规来源**：用户放入 `laws/` 的法规/标准/规范文件是**唯一**合法依据来源，不得凭模型记忆生成法规条文。
- **审查方法**：规则快筛（不调用 LLM）与 LLM 深度审查双轨并行，再经交叉审计、复核、终审三步收口。

完整规则见 [SKILL.md](SKILL.md)，逐阶段要求见 [prompts/](prompts/)。

---

## 为什么要这么设计

预案合规审查用单一方法做不好，两种失效模式恰好互补：

- **纯规则匹配**能稳定抓出结构性缺陷（要素缺失、编号断裂、法定表述缺漏），但抓不到语义问题。
- **纯大模型审查**能抓出职责不清、程序衔接断裂这类隐性问题，但会漏检，也会凭记忆编造法规条文和条款号。

所以设计成双轨独立执行、独立编号、原始结果各自落盘不被覆盖，再用交叉审计裁定分歧。关键在于**"两轨不一致"必须被显式处理**，而不是被合并掩盖：

| 5A 规则 | 5B 大模型 | 裁定 |
|---------|-----------|------|
| fail | fail | 保留（高置信度） |
| fail | pass | 标记待复核（疑规则误报） |
| pass | fail | 保留（LLM 独有隐性问题） |
| error | * | 保留有效那一侧 / 标记失败 |

另一条核心约束是**依据不成立的问题不是低置信度问题，它不是问题**。所有问题的 `reference` 必须能在知识库元数据中精确匹配，且 `article`（条款号）、`clause_text`（条文原文 ≥30 字）、`suggestion`（修订方向）三项非空——缺任一项即被移出问题清单、不占编号、不流向下游。

## 工作流架构

```
Agent0  预案画像与类型判定       ← 决定后续所有阶段的适用范围
   ↓
Agent1  本地法规盘点            ← 唯一取材口：laws/
   ↓
Agent2  法规分类               ← 效力层级 + 与本预案的相关性
   ↓
Agent3  知识库构建             ← ChromaDB，按章-节-条-款切片
   ↓
Agent4  预案条款拆分            ← CLAUSE-001 起连续编号
   ↓
[模型配置]                     ← 唯一人机交互点：模型/并发/batch/temperature
   ↓
Agent5A 规则快筛 ──┐           不调用 LLM，规则 + 知识库 Top20
Agent5B LLM 深审 ──┤           逐条调用大模型 + Top20 检索
   ↓              │
Agent5C 交叉对比审计 ←┘         决策矩阵 + 依据门禁 + 跨条款聚合
   ↓
Agent5D 交叉审计复核            裁定"待复核"，Top20 重检索验证
   ↓
Agent5E 最终审计               编号/格式/引用/一致性终审
   ↓
Agent6  法规依据复核            只补强依据，不新增问题
   ↓
Agent7  联网核验               只核验已发现问题，不新增
   ↓
Agent8  成果汇总               4 份交付物 + 能力边界声明
```

### 三层规则库

规则本身**不得携带任何法规名称、文号、标准号、法定时限**——只写检查点与触发特征，依据一律现场从知识库检索取得。这是防幻觉的关键：规则里写死法规名，等于绕过"依据只能来自 `laws/`"这条边界。

- **第一层 `R-COM-*`**：全部预案类型强制启用（要素完整性、分级、响应启动权限、信息报告时限、预案管理程序等）
- **第二层 事件类别专属**：`R-HAZ` 危化品 / `R-MIN` 矿山 / `R-FIR` 消防 / `R-TRA` 交通 / `R-ENV` 环境 / `R-NAT` 自然灾害 / `R-PHE` 公共卫生 / `R-SOC` 社会安全 / `R-EVT` 重大活动
- **第三层 层级/主体专属**：`R-GOV` 政府 / `R-ENT` 企业 / `R-SIT` 现场处置方案 / `R-GRA` 基层组织

未启用的规则组必须写入 `skipped_rules` 并注明原因——让"没跑"和"跑了没问题"永远可区分。

## 实跑数据驱动的优化

本版本基于一次真实审查（一份区级危险化学品事故应急预案，137 个条款，14 份法规文件）的输出结果做了系统性修正。原版输出 52 个问题，逐项核查后发现：

| 指标 | 实测 | 问题 |
|------|------|------|
| 输出问题数 | 52 | — |
| 依据在知识库内的 | **18** | 34 个引用了 `laws/` 中不存在的法规 |
| 去重后真正不同的发现 | **10** | 同一缺陷被按条款拆成多个编号 |
| 最重复描述的出现次数 | **19** | 一条规则命中 19 个条款 = 19 个编号 |
| 填了 `article` 条款号 | 5 / 52 | 缺条号则无法核验条款是否平移 |
| 填了 `suggestion` 修订建议 | **0 / 52** | 用户拿到问题不知道该改什么 |
| 5B 深审判 fail | 5 / 137 | 5A 同批条款发现 34 条，5B 系统性宽松 |

针对六个根因的修正：

1. **规则库硬编码法规名** → 新增"规则不得自带法规名/文号/标准号"铁律 + 依据落实门禁；新增 `kb_gap_report.json` 如实记录因知识库缺法规而审不了的检查点。
2. **无依据问题只降置信度就放行** → 改为硬拦截，移入 `rejected_problems.json`，不占编号、不入下游。
3. **同一缺陷按条款拆成 N 个编号** → 5A 跨条款聚合 + 5C 同因归并（`finding_scope: systemic`），问题编号数反映**不同缺陷数**而非命中次数。
4. **5B 系统性宽松（96.4% pass）** → 新增 `checked_dimensions` / `pass_justification` / `suspected_issues` 强制字段；检索档位与 5A 对齐到 Top20；pass 率 >90% 触发 `pass_rate_alert` 强制重审 5A 判 fail 而 5B 判 pass 的条款。
5. **大批量条款的分批执行未固化** → 写入 5B 作为条款数 >40 时的强制模式，batch 文件自带检索结果使子智能体无需继承主上下文，含断点续跑与批次完整性校验。
6. **`article` / `suggestion` 大面积空缺** → 设为跨阶段必填门禁，5E 终审加检查，非空率必须 100%。

Agent8 报告结构前置了**"本次审查的能力边界"**专节，量化告知有多少法定检查点因依据缺失未能形成结论，并强制写明一句话结论：「未形成结论 ≠ 该项合规」。

> 按新流程，同一份预案的输出预期会从 52 条降到 10 条左右——这不是漏审，是把 34 条无依据条目移出、把 19 条重复合并。想恢复覆盖度需要往 `laws/` 补充相应主题的法规，`kb_gap_report.json` 会自动告知缺哪些主题。

## 快速开始

### 1. 准备资料

```
laws/    放入法规、标准、规范性文件（PDF / DOCX / TXT / MD）
plan/    放入待审预案
```

本仓库**不含**法规文件和预案样例（法规会修订，仓库内的副本会过期变成错误依据；预案含真实联系人信息）。需要自行准备，建议从官方来源获取现行有效版本：全国人大网、中国政府网、应急管理部及各主管部委、地方人民政府官网、国家标准全文公开系统。

一份危化品类预案的典型法规基线约需覆盖：安全生产、消防、生产安全事故应急（条例 + 预案管理办法 + 事故报告调查处理）、危险化学品安全管理、应急预案编制导则、应急装备配备标准、突发事件应对（省级条例）、预警信息发布、地方预案管理办法。

### 2. 驱动执行

让 agent 读取入口文件并按总控流程执行：

```text
请读取 SKILL.md 与 prompts/master.md，严格按总控流程执行。先只执行 Agent0，完成后落盘输出文件，然后停下来汇报。
```

Codex CLI 用户可直接：

```bash
codex --cd emergency-plan-compliance-review --sandbox workspace-write --ask-for-approval on-request
```

### 3. 逐阶段推进

**首次运行不建议全流程连跑**，应在三处停下人工确认：

- **Agent0 后**：看预案类型判定对不对（判错会污染下游全部阶段）
- **Agent3 后**：跑 5 条测试检索看召回质量（5A 和 5B 共用同一知识库，这是双轨设计唯一的共因失效点）
- **Agent4 后**：看条款拆分覆盖度与 `element_tag` 标注

## 打包上传

```bash
python scripts/package_skill.py
```

生成 `dist/emergency-plan-compliance-review.zip`，其**根目录直接包含 SKILL.md**，因此可被支持 skill 包的平台直接识别。脚本会在打包后重新读取 zip 校验入口位置。

仅校验结构不打包：

```bash
python scripts/package_skill.py --check
```

默认不打包 `laws/`、`plan/`、`output/` 中的资料，需要连示例一起打包时加 `--with-samples`。

## 目录结构

```
emergency-plan-compliance-review/
├── SKILL.md            # 入口（frontmatter: name/description）
├── AGENTS.md           # Codex / 通用 agent 入口
├── CLAUDE.md           # Claude Code 入口
├── references/
│   ├── plan_type_matrix.md   # 预案类型→法规基线映射（检索线索，非可引用依据）
│   └── issue_types.md        # 问题类型枚举（唯一合法取值来源）
├── prompts/
│   ├── master.md             # 总控：任务分解、执行顺序、总体验收
│   └── 00~08/prompt.md       # 13 个阶段的完整规格
├── scripts/package_skill.py  # 打包与结构校验
├── laws/               # 用户提供的法规/标准文件（不入库）
├── plan/               # 待审预案（不入库）
└── output/             # 全部产出（不入库）
```

设计上**入口薄、规格厚**：agent 先读 SKILL.md 建立边界，再读 master.md 拿流程，执行某阶段时只读该阶段 prompt，避免一次性把 13 个阶段全灌进上下文导致注意力稀释。

`references/plan_type_matrix.md` 中的法规名称、文号、年份**只是"应该去找什么"的检索线索，不是可直接引用的依据**——必须在 `laws/` 有对应文件才能落实为审查依据。

## 边界

- **只审法律法规问题**。严禁纳入实操可行性、资源配置是否合理、PPE 是否合理、疏散距离是否科学、地方适配性、事故案例经验、专家经验判断、写作风格、错别字。
- **知识库只能来自 `laws/`**，不得凭模型记忆生成法规条文。取不到依据就记入 `kb_gap_report.json`，不生成问题。
- **Agent6 / Agent7 不得新增问题**：Agent6 只补强已有问题的遗漏依据，Agent7 只核验已发现问题（法规是否现行有效、条款号是否准确、条文是否一致），不得扩大范围、改变编号。
- **核验不到就记 `unverified`**，禁止编造条文或结论。
- 每一条款独立检查，每一个问题可追溯到具体条款 + 具体法规条文；禁止抽样或代表性检查。

## 注意

- `output/model_config.json` 会包含 API key，已在 `.gitignore` 中忽略，请勿提交。
- Agent7 联网核验会向法规官网发起请求；运行环境无网络时相应问题标为 `unverified`，据此降低置信度。
- 本版本的改动集中在提示词与规格层，新引入的数量等式（`raw_issues_in − rejected − merged == final_issues`、`systemic_findings + clause_level_findings == final_issues`）与跨条款聚合逻辑**尚未经端到端实跑验证**。
- 整条流水线是串行强依赖的：Agent0 判错类型会污染下游全部阶段，Agent3 召回质量不佳会同时拖垮 5A 和 5B。
